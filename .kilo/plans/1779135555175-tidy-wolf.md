# Plan: Wishlist & Search UX/UI Improvements

**Goal**: Address tester feedback regarding wishlist/search behavior and improve the overall UX/UI experience.

## Context

Tester reported several issues on 2026-05-18:

1. **Unexpected automatic searches**: Seeing searches that aren't in their wishlist (but somewhat related)
2. **Unexpected automatic downloads**: Downloads starting that they didn't initiate
3. **Search result accumulation**: Wishlist interval set to 21600s (6 hours), but searches run without end, filling up results over days
4. **Wishlist UX limitations**: Wants better integration between wishlist and search results
   - Ideally merge wishlist entries with their search results
   - "Unseen results" marker to track new findings
   - Filters properly integrated with wishlist (unlike other clients)
   - Persistent wishlist entries that survive restarts (other clients forget results on restart)

## Root Cause Analysis

### 1. Auto-replace feature (likely culprit for unexpected activity)

From logs: `Search completed: source=auto-replace query='The Adicts - Runaway'`

The **auto-replace** feature appears to be running automatically and:
- Searching for alternative versions of files
- Auto-downloading replacements based on "smart ranking"
- Not clearly visible/controllable in the UI

Example: User has specific wishlist entries like `"Adicts 2002 The Collection flac"` but auto-replace is finding broader matches like `"The Adicts - Runaway"`.

### 2. Search history retention

- Searches are stored in SQLite `Searches` table with no automatic cleanup
- Recently added `SearchStartedAt` index (gotcha 0z448) helps with performance but doesn't address accumulation
- Users have no way to clear old search results or set retention policies

### 3. Wishlist-search integration gap

Current architecture:
- Wishlist items trigger searches → create separate Search records
- Search results live in their own table/UI
- No direct link showing "these results came from this wishlist item"
- No way to mark results as "seen" or "reviewed"

## Proposed Solution

### Phase 1: Immediate Fixes (High Priority)

#### 1.1 Auto-Replace Visibility & Control

**Backend changes:**
- Add UI-accessible auto-replace status endpoint (already exists: `/api/v0/transfers/downloads/auto-replace/status`)
- Ensure auto-replace state persists properly (already implemented in `AutoReplaceBackgroundService`)

**Frontend changes:**
- Add Auto-Replace control panel to Transfers page
  - Show enabled/disabled status
  - Show last run time
  - Show interval setting
  - Add Enable/Disable toggle
  - Add "Run Now" manual trigger button
  - **Tooltips explaining what auto-replace does and why it's running searches**

**Files to modify:**
- `src/web/src/components/Transfers/Transfers.jsx` (add Auto-Replace section)
- `src/web/src/lib/transfers.js` (add auto-replace API functions)

#### 1.2 Search Source Attribution

**Backend changes:**
- Add `source` field to Search model (distinguish "manual", "wishlist", "auto-replace")
- Populate source when creating searches
- Add API filter to get searches by source

**Frontend changes:**
- Display search source in search list (badge/label)
- Add filter dropdown: "All Sources", "Manual", "Wishlist", "Auto-Replace"
- Color-code or icon-code different sources

**Files to modify:**
- `src/slskd/Search/Search.cs` (add Source property)
- `src/slskd/Search/SearchDbContext.cs` (migration for Source column)
- `src/slskd/Search/SearchService.cs` (populate Source)
- `src/web/src/components/Search/Searches.jsx` (add source filter UI)

#### 1.3 Search Result Retention Management

**Backend changes:**
- Add config options for search retention:
  - `searches.max_age_days` (default: 30)
  - `searches.max_count` (default: 1000)
- Add background cleanup job that runs daily
- Add manual cleanup endpoint: `POST /api/v0/searches/cleanup`

**Frontend changes:**
- Add "Clear Old Searches" button to Searches page
- Add settings in System → Search for retention policies
- Show current search count vs. max

**Files to modify:**
- `src/slskd/Core/Options.cs` (add retention options)
- `src/slskd/Search/SearchService.cs` (add cleanup method)
- `src/slskd/Search/API/Controllers/SearchesController.cs` (add cleanup endpoint)
- `src/web/src/components/Search/Searches.jsx` (add cleanup button)
- `src/web/src/components/System/System.jsx` (add retention settings)

### Phase 2: Enhanced Wishlist-Search Integration (Medium Priority)

#### 2.1 Link Wishlist Items to Their Searches

**Backend changes:**
- Add `wishlist_item_id` foreign key to Search table (nullable)
- Populate when wishlist creates a search
- Add endpoint: `GET /api/v0/wishlist/{id}/searches` (get all searches for a wishlist item)

**Frontend changes:**
- On wishlist detail/expanded view, show recent searches for that item
- Add "View All Results" button that filters search list by wishlist item
- Show count of new results since last viewed

**Files to modify:**
- `src/slskd/Search/Search.cs` (add WishlistItemId property)
- `src/slskd/Search/SearchDbContext.cs` (migration + foreign key)
- `src/slskd/Wishlist/API/Controllers/WishlistController.cs` (add searches endpoint)
- `src/web/src/components/Wishlist/Wishlist.jsx` (expand to show related searches)

#### 2.2 "Unseen Results" Tracking

**Backend changes:**
- Add `last_viewed_at` timestamp to WishlistItem
- Update when user views search results for that wishlist item
- Add `unviewed_result_count` computed property (searches newer than last_viewed_at)

**Frontend changes:**
- Show badge on wishlist items with unseen result count
- Mark wishlist item as "viewed" when user opens related search
- Add "Mark All as Viewed" action

**Files to modify:**
- `src/slskd/Wishlist/Types/WishlistItem.cs` (add LastViewedAt)
- `src/slskd/Wishlist/API/Controllers/WishlistController.cs` (add mark-viewed endpoint)
- `src/web/src/components/Wishlist/Wishlist.jsx` (show unseen badge, add mark-viewed)

#### 2.3 Improved Filter Integration

**Current state check needed:**
- Wishlist items already have a `Filter` field (line 68 in Wishlist.jsx shows it)
- Filters are already editable in the wishlist modal
- **Need to verify filters are actually applied during wishlist searches**

**If filters aren't being applied:**
- Fix `WishlistService.ExecuteWishlistSearchAsync` to apply the filter
- Add test coverage for filtered wishlist searches

**Frontend polish:**
- Add filter syntax help/examples in wishlist modal
- Show filter validation errors before saving
- Add common filter presets (FLAC only, album, etc.)

### Phase 3: Advanced UX (Lower Priority, Future Enhancement)

#### 3.1 Unified Wishlist-Search View

**Concept**: Single page that shows wishlist items with their results inline

**Design approach:**
- Collapsible wishlist item cards
- When expanded, show matching search results underneath
- Quick actions: download, re-search, mark as found
- Replaces separate Wishlist and Searches pages (or alternative view mode)

#### 3.2 Smart Wishlist Management

**Features:**
- Auto-disable wishlist items after N successful downloads
- Suggest wishlist items based on download patterns
- Bulk operations: enable/disable/delete multiple items
- Import from external sources (already has CSV import)

## Technical Considerations

### Database Migrations

**Required schema changes:**
1. `Searches.Source` (varchar, nullable, default to "manual" for existing)
2. `Searches.WishlistItemId` (guid, nullable, foreign key to WishlistItems)
3. `Searches.CreatedAt` index (if not exists - for retention cleanup)
4. `WishlistItems.LastViewedAt` (datetime, nullable)

**Migration strategy:**
- Add idempotent migrations in `SearchDbContext` and `WishlistDbContext`
- Follow existing HashDb migration pattern (see ADR-0002 code patterns)
- Handle existing data: backfill `Source = "manual"` for old searches

### API Compatibility

**New endpoints:**
- `GET /api/v0/transfers/auto-replace/status` (already exists)
- `POST /api/v0/transfers/auto-replace/enable` (already exists)
- `POST /api/v0/transfers/auto-replace/disable` (already exists)
- `POST /api/v0/searches/cleanup` (new)
- `GET /api/v0/wishlist/{id}/searches` (new)
- `POST /api/v0/wishlist/{id}/mark-viewed` (new)

**Breaking changes:** None (all additive)

### Config Changes

**New options in `config/slskd.example.yml`:**
```yaml
searches:
  retention:
    max_age_days: 30  # Auto-delete searches older than this
    max_count: 1000   # Keep at most this many searches
    cleanup_interval: 86400  # Daily cleanup (seconds)
```

## Questions for User

1. **Priority confirmation**: Is Sprint 1 (auto-replace visibility + source attribution + manual cleanup) the right immediate focus?

2. **Auto-replace behavior**: Should we recommend users disable auto-replace entirely, or is it a feature they'd want once they understand it better?

3. **Search retention defaults**: Is 30 days / 1000 searches a reasonable default, or should it be more/less aggressive?

4. **Unified view priority**: How important is the "unified wishlist-search view" (Phase 3.1)? That's a bigger UX change.

5. **Backwards compatibility**: Existing search records have no `Source` field. Should we:
   - Backfill them as "manual" (default assumption)?
   - Leave them NULL and show "Unknown" in the UI?
   - Add a migration that tries to infer source from search text patterns?

6. **Filter verification**: Should we first verify that wishlist filters are actually being applied during searches? This might be a hidden bug causing the tester's broad match issue.
